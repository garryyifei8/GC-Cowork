Core Principles
设计原则

四条不可妥协的工程化治理原则，指导所有工具选择和规则设定。

⚙

机械执行 > 文档约定

能被工具自动强制执行的规则，绝不依赖口头约定或文档要求。Pre-commit hook 检查替代"请记住格式化代码"。

▲

渐进式采用

新规则先设为 warn，团队适应后再升级为 error。避免一次性引入大量破坏性变更。

📚

Repo 即唯一真相源

所有配置、规范、文档、ADR 都在仓库内。不依赖外部 Wiki、Notion 或口头传达。克隆仓库 = 获得全部上下文。

⚡

最小必要复杂度

只添加当前需要的配置。不为假设性需求过度设计。三行重复代码好过一个过早抽象。

Enforcement Model
拦截层级详解

每层拦截的时机、内容和使用的工具。越早发现问题，修复成本越低。

Gradual Adoption
渐进式升级路线

ESLint 规则从 warn 逐步升级为 error 的计划路径。

Phase 0 — 初始化 已完成

所有规则设为 warn，不阻断任何流程。团队零摩擦适应。

Phase 1 — 当前状态 进行中

118 个 warnings（0 error）。开发者在编辑器中看到提示，但不影响提交和 CI。

Phase 2 — 收紧高优先级规则

将 no-unused-vars 和 rules-of-hooks 升级为 error。修复现有违规后执行。

Phase 3 — 收紧类型安全

将 no-explicit-any 升级为 error。逐步消除所有 any 使用。

Phase 4 — 全面 error

所有规则升级为 error。零 warning 策略。CI 全面阻断。

Commit Convention
提交消息规范

所有提交必须遵循 Conventional Commits 格式，由 commitlint 自动强制执行。

<type>(scope): subject

Type (必填)

feat — 新功能
fix — Bug 修复
refactor — 重构
docs — 文档
test — 测试
chore — 构建/工具
ci — CI/CD
style — 格式

Scope (建议填写)

app admin landing player shared backend gpu-worker infra docs

Subject 规则

✓ 小写字母开头
✓ 不以句号结尾
✓ 祈使语气 (add, fix, update)
✓ ≤ 72 字符

示例

✓ feat(app): add dark mode toggle
✓ fix(backend): resolve auth token expiry bug
✓ chore(infra): update CI workflow for Node 20
✗ updated the login page — 缺少 type 和 scope
✗ feat: Add New Feature. — 大写开头 + 句号结尾
