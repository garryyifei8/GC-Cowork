## 1. 概述

牛油果CoWork后端基于 **Python FastAPI** 框架构建，是一个AI原生的项目协作平台服务端。平台面向政府专项债咨询、展馆博物馆EPC工程、信息化智能化项目等行业场景，提供智能对话驱动的项目全生命周期管理能力。

### 1.1 技术栈

| 组件 | 技术选型 | 说明 |
|------|---------|------|
| Web框架 | FastAPI | 异步高性能Python Web框架 |
| 数据校验 | Pydantic v2 | 类型安全的数据模型定义与序列化 |
| HTTP客户端 | httpx | 异步HTTP客户端，用于调用LLM API |
| LLM服务 | DeepSeek API | OpenAI兼容的聊天补全接口 |
| 数据存储 | 内存字典 | 当前阶段使用内存存储，预留数据库迁移接口 |
| 流式传输 | SSE (Server-Sent Events) | 实时流式输出AI回复内容 |

### 1.2 核心设计理念

- **Agent驱动架构**：通过调度Agent（Dispatch）识别用户意图，路由至8个专业领域Agent处理
- **对话即操作**：用户通过自然语言对话完成项目管理、财务、人事等操作
- **卡片化输出**：Agent返回结构化的交互式卡片（InteractiveCard），前端渲染为可操作的UI控件
- **流式响应**：支持SSE流式输出，提升对话体验

## 3. Agent系统

Agent系统是平台的核心，采用 **调度-专家** 两层架构。所有用户输入首先经过调度Agent（Dispatch），由其识别意图并路由至对应的专业Agent。

### 3.1 BaseAgent 抽象基类

`src/agents/base.py` 定义了所有Agent的公共接口：

```
BaseAgent (ABC)
├── agent_type: AgentType          # Agent类型标识
├── system_prompt: str             # 系统提示词
├── llm_client: LLMClient         # 共享的LLM客户端
├── handle(request) -> response    # [抽象] 处理请求
├── _build_messages(request)       # 构建LLM消息列表 [system, ...history, user]
├── build_stream_messages(request) # 构建流式模式消息（追加自然语言指令）
├── _base_response(request, content) # 构建基础响应
└── _parse_cards(raw_cards)        # 解析LLM JSON输出为InteractiveCard
```

**消息构建流程：**

1. 系统提示词（`system_prompt`）作为首条消息
2. 从`request.context["history"]`提取对话历史
3. 当前用户消息追加到末尾
4. 流式模式额外追加"使用自然语言回复"的指令

**卡片解析逻辑：**

`_parse_cards` 方法将LLM返回的JSON中的`cards`数组转换为`InteractiveCard`模型列表。支持11种卡片类型（action/data/form/file/alert/task_list/kanban/progress/table/chart/report），未识别类型回退为`DATA`。

### 3.2 DispatchAgent 调度Agent

`src/agents/dispatch.py` 是所有对话的入口，职责包括：

1. **意图识别**：调用LLM以JSON模式分析用户意图，返回`AgentIntent`
2. **Agent路由**：根据`primary_agent`字段路由到对应专业Agent
3. **闲聊处理**：当`primary_agent`为`dispatch`时直接返回回复

**意图识别的JSON输出格式：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `primary_agent` | string | 主处理Agent（project/finance/legal/procurement/hr/bidding/document/knowledge/dispatch） |
| `secondary_agents` | string[] | 可能需要协同的其他Agent |
| `complexity` | string | simple（简单查询）或 complex（综合分析） |
| `workflow_pattern` | string | serial（串行）/ parallel（并行）/ human_in_loop（需人工确认） |
| `confidence` | float | 0.0~1.0 的置信度 |
| `reply` | string | 给用户的简短自然语言回复 |

**路由流程：**

```
用户消息 → DispatchAgent.handle()
  ├── LLM意图识别 (chat_json)
  ├── 解析 AgentIntent
  ├── primary_agent == DISPATCH → 直接返回reply
  └── primary_agent == 其他 → registry查找 → 目标Agent.handle() → 返回响应
```

### 3.3 Agent注册表

`src/agents/registry.py` 提供 `create_agent_registry(llm_client)` 函数，返回 `dict[AgentType, BaseAgent]` 映射：

| AgentType | Agent类 | 职能领域 |
|-----------|---------|---------|
| DISPATCH | DispatchAgent | 意图识别、路由调度 |
| PROJECT | ProjectAgent | 项目进度、里程碑、风险、资源 |
| FINANCE | FinanceAgent | 费用审核、预算分析、发票核验 |
| LEGAL | LegalAgent | 合同审查、合规检查、法律风险 |
| PROCUREMENT | ProcurementAgent | 供应商匹配、采购跟踪、比价 |
| HR | HRAgent | 考勤、绩效、招聘、政策问答 |
| BIDDING | BiddingAgent | 招标监测、标书生成、中标评估 |
| DOCUMENT | DocumentAgent | 文档生成、模板填充、版本管理 |
| KNOWLEDGE | KnowledgeAgent | 经验检索、案例推荐、标准查询 |

### 3.4 专业Agent处理流程

以 `ProjectAgent` 为例说明典型的Agent处理流程：

1. **构建项目上下文**：调用 `_build_project_context()` 序列化当前所有项目数据（名称、类型、阶段、进度、预算、任务统计、可推进阶段等）
2. **注入上下文到消息**：在system prompt之后插入项目数据消息
3. **调用LLM获取结构化响应**：`chat_json` 获取 `{reply, cards}` 格式的JSON
4. **解析卡片**：`_parse_cards` 将原始JSON卡片转为 `InteractiveCard`
5. **构建AgentResponse**：组装最终响应

**流式模式**差异：
- 使用 `build_stream_messages` 构建消息（追加自然语言回复指令）
- 通过 `chat_stream` 逐token输出
- 卡片通过并发的 `handle()` 调用异步生成

## 4. LLM集成

### 4.1 LLMClient

`src/llm/client.py` 封装了与DeepSeek API的所有交互，使用 httpx 异步HTTP客户端。

**三种调用模式：**

| 方法 | 用途 | temperature | 返回类型 |
|------|------|------------|---------|
| `chat()` | 普通文本对话 | 0.7 | `str` |
| `chat_json()` | 结构化JSON输出 | 0.3 | `dict` |
| `chat_stream()` | 流式token输出 | 0.7 | `AsyncIterator[str]` |

**关键配置参数：**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `api_base` | `https://api.deepseek.com` | API基础URL |
| `model` | `deepseek-chat` | 模型名称 |
| `timeout` | 60秒 | 普通请求超时 |
| `_STREAM_TIMEOUT` | 120秒 | 流式请求超时 |

**chat_json 的 JSON模式：**

通过 `response_format: {"type": "json_object"}` 指令要求LLM输出合法JSON。解析失败时抛出 `LLMResponseError`。

**chat_stream 的SSE解析：**

流式模式使用 httpx 的 `stream()` 方法，按SSE协议解析：
- 以 `\n\n` 分割事件
- 解析 `data: ` 前缀的行
- `data: [DONE]` 表示流结束
- 从 `choices[0].delta.content` 提取增量内容

**异常体系：**

| 异常 | 触发场景 |
|------|---------|
| `LLMAuthError` | API key无效（401） |
| `LLMConnectionError` | 连接超时/失败 |
| `LLMResponseError` | 非200响应/JSON解析失败 |

### 4.2 提示词工程

`src/llm/prompts.py` 为每个Agent定义了专门的系统提示词。

**DISPATCH_SYSTEM_PROMPT：** 定义调度规则，要求以JSON格式输出意图分类结果。

**专业Agent提示词结构：**

每个Agent的system prompt包含以下部分：
1. **角色定义**：明确Agent的专业领域
2. **能力清单**：列出Agent可以处理的任务类型
3. **行业背景**：政府专项债、EPC工程、信息化项目
4. **输出格式**：要求以 `{reply, cards}` JSON格式返回
5. **CARD_FORMAT_GUIDE**：共享的卡片类型使用规范

**CARD_FORMAT_GUIDE 核心规则：**

- 优先使用可交互控件（task_list/kanban/progress/table/chart），禁止用data卡片展示任务/项目数据
- task的status和priority必须使用英文枚举值
- 每次最多返回3张卡片
- 每张卡片必须包含actions（后续操作建议），提供2-4个可执行的按钮标签
- 简单闲聊对话cards为空数组

## 5. Store层

Store层采用模块级Python字典作为内存存储，提供统一的CRUD接口模式。

### 5.1 通用模式

每个Store模块遵循相同的结构：

```python

_items: dict[str, Model] = {}
_seeded: bool = False

# 种子数据函数
def seed_xxx() -> None: ...

# CRUD接口
def list_xxx(**filters) -> list[Model]: ...
def get_xxx(id: str) -> Model | None: ...
def create_xxx(data) -> Model: ...
def update_xxx(id: str, updates: dict) -> Model | None: ...
def delete_xxx(id: str) -> bool: ...
```

### 6.2 对话API详细

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/chat` | 简单对话 — 前端主用端点，接收 `{message, context?}` 返回 `{reply, agent_type, cards}` |
| POST | `/api/chat/stream` | SSE流式对话 — 返回 `text/event-stream`，事件类型：`token`/`done`/`error` |
| POST | `/api/chat/message` | 会话消息 — 带session管理的完整对话 |
| POST | `/api/chat/sessions` | 创建会话 |
| GET | `/api/chat/sessions` | 列出用户会话 |

**流式对话流程：**

```
请求 → 意图分类(chat_json, 非流式)
     → 确定目标Agent
     → 并行执行:
         ├── 流式文本输出 (SSE token事件)
         └── 卡片生成 (chat_json, 非流式)
     → 发送done事件 (含agent_type + cards)
```

## 7. 数据模型

| 枚举 | 值域 | 用途 |
|------|------|------|

| ApprovalStatus | pending/approved/rejected | 审批状态 |

### 7.2 核心业务模型

**Project（项目）：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | str | 项目ID |
| name | str | 项目名称 |
| project_type | str | 类型（EPC/信息化/专项债） |

| budget | float | 预算金额 |
| actual_spend | float | 实际支出 |
| risks | list[RiskItem] | 风险列表 |
| milestones | list[dict] | 里程碑列表 |
| team_members | list[str] | 团队成员 |
| status | str | 状态标签（active/risk/planning/completed） |
| due_date | str | 截止日期 |

**ProjectTask（任务）：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | str | 任务ID |
| project_id | str | 所属项目ID |
| name | str | 任务名称 |
| assignee | str | 负责人 |
| status | TaskStatus | 任务状态 |
| priority | TaskPriority | 优先级 |
| due_date | str | 截止日期 |
| description | str | 描述 |

### 7.3 Agent系统模型

- **AgentIntent**：意图识别结果 — primary_agent, secondary_agents, complexity, workflow_pattern, confidence
- **AgentRequest**：Agent请求 — request_id, session_id, agent_type, user_message, context, intent
- **AgentResponse**：Agent响应 — request_id, agent_type, content, cards, requires_human_confirmation
- **InteractiveCard**：交互卡片 — card_type, title, data, actions

### 7.4 其他领域模型

- **Employee** / **AttendanceRecord** / **LeaveRequest** / **SalaryRecord**：人事模型
- **ExpenseReport** / **BudgetLine** / **Invoice**：财务模型
- **Notice** / **VehicleRequest**：OA模型
- **ProcurementPackage**：采购包模型
- **ProcessRecord**：过程记录模型
- **BiddingOpportunity**：投标机会模型
- **DocumentItem**：文档模型
- **KnowledgeItem**：知识库模型

## 8. 异常处理

系统定义了统一的异常处理体系：

| 异常类 | HTTP状态码 | 说明 |
|--------|-----------|------|
| PlatformError | 500 | 平台通用错误基类 |
| ProjectNotFoundError | 404 | 项目未找到 |
| TaskNotFoundError | 404 | 任务未找到 |
| SessionNotFoundError | 404 | 会话未找到 |
| LLMAuthError | 401 | LLM API密钥无效 |
| LLMConnectionError | 503 | LLM连接失败/超时 |
| LLMResponseError | 502 | LLM返回异常响应 |

FastAPI异常处理器注册：
- `PlatformError` → 结构化错误响应
- `HTTPException` → 标准HTTP错误
- `RequestValidationError` → 字段级422校验错误
- `Exception` → 兜底500错误

```
uvicorn src.main:app

```
