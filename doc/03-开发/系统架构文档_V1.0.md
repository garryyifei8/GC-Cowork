## 一、概述

### 1.1 系统定位

本系统是一个 **AI原生** 的项目内部协作平台，面向政府专项债咨询、展馆博物馆EPC总承包、信息化智能化项目三大业务板块。核心理念是"对话即操作"——员工通过与专业Agent对话完成日常工作，同时提供 monday.com 风格的看板、表格、甘特图等多视图操作界面。

### 1.2 核心目标

| 目标维度 | 具体指标 |
|---------|---------|
| 信息同步 | 项目信息 5 分钟内触达所有相关人员 |
| 任务协同 | 人工协调成本减少 50%+ |
| 知识沉淀 | 知识复用率提升 60%+ |
| 决策效率 | 审批周期缩短 30%+ |
| 流程合规 | 合规偏差率 < 2% |

### 1.3 技术约束

- 采用国产大模型（DeepSeek），数据不出境
- 私有化部署，满足政府项目数据安全要求
- 前后端分离，前端 React + TypeScript，后端 Python FastAPI

## 二、整体架构分层

系统采用五层架构设计：

```
┌──────────────────────────────────────────────────────────┐
│                  交互层（Interaction Layer）                │
│  对话式UI ｜ 可交互卡片 ｜ 多视图工作台 ｜ 鸟瞰可视化 ｜ 移动端 │
├──────────────────────────────────────────────────────────┤
│                 Agent 调度层（Orchestration）               │
│     意图识别 ｜ Agent路由 ｜ 多Agent协同 ｜ 会话管理          │
├──────────────────────────────────────────────────────────┤
│                 Agent 能力层（Agent Skills）                │
│  项目管理｜财务｜法务｜采购｜人事｜投标｜文档｜知识｜过控｜监理  │
├──────────────────────────────────────────────────────────┤
│                 核心引擎层（Core Engines）                   │
│  知识库引擎｜工作流引擎｜权限引擎｜学习引擎｜可视化引擎       │
├──────────────────────────────────────────────────────────┤
│                 数据与集成层（Data & Integration）            │
│  项目数据｜文档存储｜外部系统对接｜向量数据库｜审计日志        │
└──────────────────────────────────────────────────────────┘
```

### 各层职责

| 架构层 | 核心组件 | 职责 |
|-------|---------|------|
| **交互层** | 对话式UI、可交互卡片、多视图工作台、鸟瞰可视化、移动端 | 用户与系统的唯一触点，提供多模态交互体验 |
| **Agent调度层** | 意图识别、Agent路由、多Agent协同、会话管理 | 理解用户意图，将任务路由到合适的专业Agent |
| **Agent能力层** | 项目管理、财务、法务、采购、人事、投标、文档、知识Agent | 各领域专业Agent提供具体业务能力 |
| **核心引擎层** | 知识库引擎、工作流引擎、权限引擎、学习引擎、可视化引擎 | 支撑平台运行的基础能力组件 |
| **数据与集成层** | 项目数据、文档存储、外部对接、向量数据库、审计日志 | 数据持久化、外部系统集成、全链路审计 |

## 四、多Agent体系

### 4.1 架构模式

平台采用 **"1个通用调度Agent + N个专业Agent"** 的架构。调度Agent（DispatchAgent）作为前台接收所有用户对话，通过LLM进行意图识别后路由到专业Agent，或协调多Agent联合完成复杂任务。

### 4.2 Agent角色矩阵

| Agent名称 | 职责领域 | 核心能力 |
|-----------|---------|---------|
| **项目管理Agent** | 项目全周期 | 进度追踪、里程碑管理、风险预警、资源调度建议、WBS分解 |
| **财务Agent** | 财务管理 | 费用报销审核、预算对比分析、资金计划提醒、发票校验、财评协助 |
| **法务Agent** | 合同法务 | 合同条款审查、风险条款标注、合规性检查、招标文件法律审查 |
| **采购Agent** | 采购管理 | 供应商匹配推荐、比价分析、采购流程跟踪、政府采购合规校验 |
| **人事Agent** | 人力资源 | 考勤统计、绩效数据汇总、招聘进度追踪、政策答疑 |
| **投标Agent** | 投标管理 | 招标信息监控、标书框架生成、历史中标分析、资质匹配 |
| **文档Agent** | 文档处理 | 文档生成/模板填充、格式转换、版本管理、智能摘要 |
| **知识Agent** | 知识管理 | 经验检索、案例推荐、标准规范查询、新员工培训引导 |

### 4.3 多Agent协作机制

- **串行协作**：任务按顺序在多个Agent之间流转。例如采购申请流程：采购Agent -> 财务Agent -> 项目管理Agent 依次审核，每个环节的输出作为下一环节的输入。
- **并行协作**：多个Agent同时工作，结果由调度Agent汇总。例如项目立项评估：法务、财务、采购、项目管理Agent 同时输出评估意见，生成综合评估报告。
- **人机协同**：Agent完成初步工作后，@真人员工确认或补充。所有涉及金额确认、合同签署、审批放行等操作必须经过人工确认。
- **联动预警**：过控Agent检测到异常时，自动联动对应Agent链进行分析和处理建议。

### 4.4 Agent学习与进化

- **反馈闭环**：员工对Agent输出的"采纳/修改/拒绝"均记录，用于优化后续表现
- **知识注入**：新制度、新流程发布后自动更新对应Agent的知识上下文
- **Skill插件化**：Agent能力以Skill插件形式开发，支持热插拔和独立迭代

## 五、LLM集成架构

本节描述LLM与Agent体系的具体集成方案，基于 DeepSeek API（OpenAI兼容协议）实现全链路智能化。

### 5.1 LLMClient层

**文件位置**: `src/llm/client.py`

LLMClient 是与 DeepSeek API 交互的统一封装层，基于 `httpx.AsyncClient` 实现异步调用。

```python
class LLMClient:
    async chat(messages, temperature, max_tokens) -> str
    async chat_json(messages, ...) -> dict  # response_format=json_object
```

**关键设计**：

- 使用 `httpx.AsyncClient` 异步 POST 请求 `{api_base}/chat/completions`
- 超时策略：简单任务 3s，复杂任务 15s（通过 `TaskComplexity` 枚举控制）
- 模型选择：按任务复杂度在 `llm_simple_model` 和 `llm_complex_model` 之间动态切换
- 错误策略：失败直接抛出 `LLMError`，不做 fallback

### 5.2 Prompt模板体系

**文件位置**: `src/llm/prompts.py`

系统为调度Agent和8个专业Agent各定义一个 system prompt 常量：

| 常量 | 用途 |
|------|------|
| `DISPATCH_SYSTEM_PROMPT` | 意图识别，输出结构化 JSON（primary_agent, secondary_agents, complexity, workflow_pattern, confidence, reply） |
| `PROJECT_SYSTEM_PROMPT` | 项目管理专家（政府专项债/EPC/信息化） |
| `FINANCE_SYSTEM_PROMPT` | 财务专家（预算/报销/资金计划） |
| `LEGAL_SYSTEM_PROMPT` | 法务专家（合同审查/合规检查） |
| `PROCUREMENT_SYSTEM_PROMPT` | 采购专家（供应商/询价比价） |
| `HR_SYSTEM_PROMPT` | 人事专家（考勤/绩效/招聘） |
| `BIDDING_SYSTEM_PROMPT` | 投标专家（标书分析/中标概率） |
| `DOCUMENT_SYSTEM_PROMPT` | 文档专家（文档生成/模板管理） |
| `KNOWLEDGE_SYSTEM_PROMPT` | 知识管理专家（经验检索/案例推荐） |

**调用方式**：
- DispatchAgent 使用 `chat_json()` 获取结构化意图 + 自然语言回复
- 专业Agent 使用 `chat()` 获取纯文本回复
- Prompt 注入会话历史（最近 N 条 messages）作为上下文

### 5.3 Agent改造

#### BaseAgent

- 注入 `LLMClient` 实例
- 新增 `_build_messages(request) -> list[dict]`：拼装 `[system_prompt, ...历史消息, 当前用户消息]`

#### DispatchAgent

1. 调用 `llm.chat_json()` 解析出 `AgentIntent` + reply
2. 根据 `primary_agent` 从注册表（`src/agents/registry.py`）获取专业Agent
3. 调用专业 `Agent.handle()` 获取领域回复
4. 若 `primary_agent=DISPATCH`（闲聊场景），则由 Dispatch 自己回复
5. 原有的 `_classify_intent()` 和 `_INTENT_RULES` 关键词匹配逻辑已删除

#### 专业Agent

所有8个专业Agent结构统一：

```python
class XxxAgent(BaseAgent):
    agent_type = AgentType.XXX
    system_prompt = XXX_SYSTEM_PROMPT

    async def handle(self, request):
        messages = self._build_messages(request)
        content = await self.llm_client.chat(messages)
        return AgentResponse(content=content, ...)
```

#### Agent注册表

**文件位置**: `src/agents/registry.py`

```python
AGENT_REGISTRY: dict[AgentType, BaseAgent]
get_agent(agent_type) -> BaseAgent
```

### 5.4 数据流

完整的请求处理流程如下：

```
用户消息
  → DispatchAgent.handle()
    → LLM chat_json() 意图识别
    → AgentIntent { primary_agent=FINANCE, complexity=SIMPLE, ... }
    → registry.get_agent(FINANCE)
    → FinanceAgent.handle()
      → _build_messages(request)   // 拼装 system_prompt + 历史 + 当前消息
      → LLM chat() 生成领域回复
    → 返回 AgentResponse
  → HTTP Response 返回前端
```

**关键路径说明**：
1. 用户消息通过 `/api/chat` 路由进入后端
2. DispatchAgent 首先通过 LLM 进行意图识别，输出结构化 JSON
3. 根据识别结果中的 `primary_agent` 字段路由到对应专业Agent
4. 专业Agent 使用自身 system prompt + 会话上下文调用 LLM 生成回复
5. 回复封装为 `AgentResponse` 返回前端渲染

### 5.5 错误处理

LLM相关异常采用分层错误体系：

```
LLMError(PlatformError)
├── LLMConnectionError  — 网络不通/超时
├── LLMAuthError        — API Key 无效 (401)
└── LLMResponseError    — 返回格式异常/JSON解析失败
```

- 所有 `LLMError` 继承自 `PlatformError`，默认 HTTP 状态码 503
- `LLMAuthError` 状态码为 401
- 异常统一冒泡到 `platform_error_handler` 中间件处理
- 不做自动重试或 fallback，直接向用户返回错误信息

## 六、安全与合规

### 6.1 数据安全

| 安全措施 | 说明 |
|---------|------|
| 全链路加密 | TLS 1.3 传输加密，数据库字段级加密 |
| 数据合规 | 符合《数据安全法》《个人信息保护法》，LLM推理数据不出境 |
| 审计日志 | 操作日志全量记录，支持审计追溯，满足跟踪审计要求 |
| 数据脱敏 | 敏感数据（合同金额、员工薪资等）脱敏后再进入LLM上下文 |

### 6.2 权限控制

- 基于 **RBAC + ABAC** 的细粒度权限控制，确保数据最小必要访问
- 知识库按密级和部门设置访问权限
- 文件级别的查看/编辑/下载权限

### 6.3 合规要求

- **等保三级**：按等保三级标准设计，满足政府项目数据安全要求
- **电子签名**：关键审批支持电子签名，符合《电子签名法》要求
- **国产化**：采用国产LLM模型和国产GPU，满足信创要求

## 七、部署方式

### 7.1 部署架构

采用 **私有化部署** 方案，考虑到政府项目数据的敏感性：

- **LLM推理**：核心LLM模型通过本地GPU服务器运行，支持国产GPU（华为昇腾、海光AI）
- **应用服务**：FastAPI 后端 + React 前端，标准容器化部署
- **辅助能力**：可选择性接入国内云端API（如OCR、语音识别等非敏感能力）

### 7.2 性能指标

| 指标 | 要求 |
|------|------|
| Agent响应时间 | 普通问答 < 3秒，复杂分析 < 15秒 |
| 并发用户数 | 200+ 用户同时在线 |
| 知识检索 | 百万级文档检索 < 2秒 |
| 系统可用性 | 99.5%（工作时间段） |
| 可视化渲染 | 仪表盘加载 < 2秒 |
| 数据刷新 | 仪表盘数据延迟 <= 5分钟 |

### 7.3 可扩展性

- **Agent Skill插件化**：能力以Skill插件形式开发，支持热插拔
- **工作流自定义**：工作流模板支持可视化自定义
- **外部集成**：对接外部系统（OA、ERP、财务系统）采用标准API网关
- **模型可替换**：支持多模型切换，不绑定单一LLM供应商
- **可视化扩展**：仪表盘组件支持自定义开发和第三方图表集成
