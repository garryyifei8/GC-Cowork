## 1. 概述

本项目前端采用以下核心技术栈:

| 技术 | 版本 | 用途 |
|------|------|------|
| React | 19.2 | UI 框架 |
| TypeScript | 5.9 | 类型安全 |
| Tailwind CSS | 4.2 | 样式系统 (Vite 插件集成) |
| Zustand | 5.0 | 状态管理 |
| Vite | 7.3 | 构建工具 |
| React Router | 7.13 | 路由管理 |
| Recharts | 3.8 | 图表库 |
| Lucide React | 0.577 | 图标库 |
| Markmap | 0.18 | 思维导图渲染 |

### 架构核心理念

前端从传统的"页面驱动"改造为**控件驱动**的统一架构。核心设计决策如下:

| 决策项 | 选择 |
|--------|------|
| 统一程度 | 完全统一 -- 页面是控件的预设组合 |
| 聊天控件交互 | 弹出到右侧内容区域 (ArtifactPanel) |
| 页面布局 | 先固定，架构预留可配置能力 |
| 控件粒度 | 三层: 原子UI -> 业务控件 -> 视图控件 |
| 迁移策略 | 重写核心层，一次性建立完整控件体系 |

这一架构使得传统功能页面和 AI 聊天弹出的控件**共享同一套组件体系**，避免了组件重复开发，同时为未来的可配置仪表盘奠定基础。

## 2. 控件化架构

### 2.1 三层控件体系

控件按职责分为三层，层级递进，上层组合下层:

```
Layer 3: 视图控件 (View Widgets)
  由业务控件组合而成，可嵌入页面或 AI 聊天 ArtifactPanel
  例: TaskKanban, GanttChart, ProjectTable, BudgetOverview

Layer 2: 业务控件 (Business Widgets)
  带业务语义的中间组件，可独立使用也可被视图控件组合
  例: TaskCard, ProjectCard, RiskItem, BudgetRow

Layer 1: 原子 UI 组件 (Atomic UI)
  无业务逻辑的纯 UI 组件，全局复用
  例: StatCard, ProgressBar, StatusBadge, DataTable, Chart
```

**设计原则:**

- Layer 1 不包含任何业务逻辑，仅处理展示
- Layer 2 承载单一业务实体的展示与交互
- Layer 3 组合 Layer 1/2 形成完整的业务视图，直接面向用户使用
- 各层通过 props 接口解耦，下层不感知上层的存在

### 2.2 Widget Registry (控件注册表)

Registry 是整个控件体系的索引中心，维护所有控件的类型定义与组件引用。页面渲染和 AI 聊天展开控件都通过同一个 Registry 查找组件。

**类型定义** (`src/widgets/types.ts`):

```typescript
export type WidgetLayer = 'atomic' | 'business' | 'view'

export interface WidgetDef<P = any> {
  type: string                                           // 唯一标识符
  layer: WidgetLayer                                     // 所属层级
  component: LazyExoticComponent<ComponentType<P>> | ComponentType<P>
  defaultProps?: Partial<P>                              // 默认属性
  defaultSize?: { cols: number; rows: number }           // 网格尺寸 (预留)
  title?: string                                         // 显示名称
  icon?: LucideIcon                                      // 图标
}
```

**Registry 实现** (`src/widgets/registry.ts`):

Registry 类提供以下 API:

| 方法 | 说明 |
|------|------|
| `register(def)` | 注册控件定义，重复注册时覆盖并警告 |
| `get(type)` | 按 type 查找控件，返回 `WidgetDef \| undefined` |
| `has(type)` | 判断控件是否已注册 |
| `getAll()` | 返回所有已注册控件 |
| `getByLayer(layer)` | 按层级筛选控件 |

**注册方式:**

- Layer 1 (原子) 和 Layer 2 (业务): **同步导入**后注册，因为体积小且使用频繁
- Layer 3 (视图): 通过 `React.lazy()` 注册为懒加载组件

```typescript
// Layer 1 同步注册示例
registry.register({
  type: 'stat_card',
  layer: 'atomic',
  component: StatCard,
  title: '统计卡片',
})

// Layer 3 懒加载注册示例
registry.register({
  type: 'task_kanban',
  layer: 'view',
  component: lazy(() => import('./views/TaskKanban')),
  title: '任务看板',
})
```

### 2.3 WidgetHost (统一渲染容器)

WidgetHost 是所有控件的统一渲染入口 (`src/widgets/WidgetHost.tsx`)，职责包括:

- 从 Registry 查找控件定义
- 合并 `defaultProps`、外部 `props` 和 `data`
- 使用 `Suspense` 包裹懒加载组件，提供骨架屏加载动画
- 使用 `ErrorBoundary` 捕获渲染错误
- 渲染可选的标题栏 (含图标)
- 支持 CSS Grid `area` 布局 (预留可配置)
- 未找到组件时渲染友好的 "WidgetNotFound" 提示

**调用方式:**

```tsx
<WidgetHost type="task_kanban" props={{ projectId: '123' }} />
```

**Props 接口:**

```typescript
export interface WidgetHostProps {
  type: string                    // 控件类型标识
  props?: Record<string, any>     // 传递给控件的属性
  data?: any                      // 直接注入的数据 (用于聊天模式)
  area?: string                   // CSS Grid 区域名
  className?: string              // 容器附加样式
  showHeader?: boolean            // 是否显示标题栏，默认 true
}
```

### 2.4 PageRenderer (声明式页面渲染器)

PageRenderer (`src/pages/PageRenderer.tsx`) 将页面定义为声明式的布局配置，遍历 slot 列表逐一渲染 WidgetHost。

**PageLayout 配置:**

```typescript
export interface WidgetSlot {
  id: string              // 唯一标识，用作 React key
  widgetType: string      // 对应 Registry 中的 type
  props?: Record<string, any>
  area?: string           // CSS Grid 区域名 (预留)
  className?: string      // slot 容器附加样式
}

export type GridType = 'single' | '2-col' | '3-col' | '4-col' | 'dashboard'

export interface PageLayout {
  title: string
  grid: GridType
  slots: WidgetSlot[]
}
```

**预设网格类型:**

| GridType | Tailwind 类 |
|----------|------------|
| `single` | `grid grid-cols-1 gap-6` |
| `2-col` | `grid grid-cols-1 md:grid-cols-2 gap-6` |
| `3-col` | `grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-6` |
| `4-col` | `grid grid-cols-1 md:grid-cols-2 lg:grid-cols-4 gap-6` |
| `dashboard` | `grid grid-cols-1 md:grid-cols-2 lg:grid-cols-4 gap-6` |

**路由使用:**

```tsx
<Route path="/tasks" element={<PageRenderer layout={tasksLayout} />} />
```

### 2.5 两条路径 (页面模式 vs AI 聊天模式)

```
路径A: 传统页面
  路由匹配 -> PageRenderer 读取 layout 配置 -> 遍历 WidgetSlot[]
  -> WidgetHost 渲染

路径B: AI 聊天
  用户提问 -> 后端返回 cards[] -> CardRenderer 显示预览
  -> 点击展开 -> WidgetHost 渲染

两条路径汇聚于:
  Widget Registry -> WidgetHost -> Zustand Stores (数据层)
```

**关键点:** 无论是页面模式还是聊天模式，最终渲染的控件是**完全相同的组件实例**。两条路径的差异仅在于数据来源 (Store 驱动 vs Props 注入) 和渲染入口 (PageRenderer vs ArtifactPanel)。

## 5. AI 聊天控件交互

### 5.1 交互流程

```
1. 用户提问 (ChatInput)
   |
2. 后端返回 cards: [{ type: 'task_kanban', data: {...} }] (API /chat/stream)
   |
3. CardRenderer 显示紧凑卡片预览 + "展开" 按钮
   |
4. 用户点击展开 -> registry.get('task_kanban') (Widget Registry)
   |
5. ArtifactPanel -> WidgetHost 渲染完整交互控件
```

**步骤 4 的关键:** `registry.get()` 返回的组件与传统页面中使用的是**完全相同的组件实例**。

### 5.2 Chat Card 预览层

现有的 10 种 Chat Card 类型 (ActionCard, AlertCard, DataCard, ChartCard, FileCard, KanbanMiniCard, ProgressCard, ReportCard, TableCard, TaskListCard) 保留为聊天气泡中的**紧凑预览**。它们的职责是:

- 在消息流中以紧凑形式展示后端返回的结构化数据
- 提供"展开"按钮，触发 WidgetHost 渲染对应的视图控件
- CardRenderer 通过 `card.type` 映射到 Registry 中的控件类型
- 后端 `InteractiveCard` 包含显式的 `widget_type` 字段，CardRenderer 优先使用该字段；若缺失，fallback 到 `detectWidgetType()` 启发式匹配

### 5.3 数据注入差异

| 模式 | 数据来源 | 机制 |
|------|----------|------|
| 页面模式 | Zustand Store | 控件通过 hooks 从 Store 获取数据，mount 时自动 fetch |
| 聊天模式 | Props 注入 | 后端返回的 `card.data` 通过 WidgetHost 的 `data` prop 传入 |

控件内部通过优先级选择:

```typescript
const data = props.data ?? useStore(selector)
```

### 6.2 主题切换 (深色/浅色)

**机制:** 基于 CSS class 的主题切换 (`darkMode: 'class'`)

- `<html>` 元素通过 `class="dark"` 控制深色模式
- 使用 Zustand `themeStore` 管理主题偏好，持久化到 `localStorage`
- 顶栏 ThemeToggle 组件 (Sun/Moon 图标) 切换主题

**控件要求:** 所有控件必须使用 Tailwind 的 dark variant:

```tsx
// 正确
<div className="bg-white dark:bg-gray-800 text-gray-900 dark:text-gray-100">

// 禁止
<div style={{ backgroundColor: '#1e293b' }}>
```

## 7. 数据层

### 7.1 Zustand Stores

项目使用 Zustand 5 进行状态管理，每个业务域对应一个独立 Store:

| Store 文件 | 职责 |
|-----------|------|
| `chatStore.ts` | 聊天消息、会话状态 |
| `projectStore.ts` | 项目数据、选中项目、视图类型 |
| `taskWorkbenchStore.ts` | 任务数据、筛选条件、看板状态 |
| `dashboardStore.ts` | 总览页统计数据 |
| `hrStore.ts` | HR 模块数据 (员工、考勤、薪资) |
| `financeStore.ts` | 财务模块数据 (预算、费用) |
| `dailyStore.ts` | "我的日常" 聚合数据 |
| `themeStore.ts` | 主题偏好 (dark/light) |
| `notificationStore.ts` | 通知消息 |

### 7.2 数据注入策略

控件支持两种数据来源，内部通过优先级选择:

```typescript
// 控件内部逻辑
const data = props.data ?? useStore(selector)
```

| 场景 | 数据来源 | 说明 |
|------|----------|------|
| 页面模式 (Store 驱动) | Zustand Store | 控件通过 hooks 订阅 Store，mount 时自动 fetch |
| 聊天模式 (Props 注入) | WidgetHost props | 后端返回的 `card.data` 通过 props 传入，控件优先使用 |

这种设计使同一个控件组件可以在两种模式下复用，无需任何条件分支。

## 8. 控件间通信

控件之间**不直接通信**。所有交互通过 Zustand Store 的共享 slice 实现单向数据流:

| 场景 | 写入方 | 读取方 | Store Slice |
|------|--------|--------|-------------|
| 筛选联动 | TaskFilters | TaskKanban / TaskList | `taskStore.filters` |
| 选中状态 | 任意控件 | 关联控件 | `projectStore.selectedProjectId` |
| 视图切换 | ViewSwitcher | 同页面视图控件 | Store 中的 `viewType` |

**架构约束:**

- 禁止控件间通过 props drilling 传递状态
- 禁止通过 React Context 在控件间共享状态
- 所有共享状态必须经由 Zustand Store

## 9. 懒加载策略

| 层级 | 加载方式 | 原因 |
|------|----------|------|
| Layer 1 (原子) | 同步加载 | 体积小，几乎每个页面都使用 |
| Layer 2 (业务) | 同步加载 | 被视图控件内部组合使用 |
| Layer 3 (视图) | `React.lazy()` 懒加载 | 体积较大，按需加载 |

Layer 3 的懒加载由 WidgetHost 中的 `Suspense` 包裹，加载期间显示骨架屏动画:

```tsx
<ErrorBoundary>
  <Suspense fallback={<WidgetFallback />}>
    <Component {...mergedProps} />
  </Suspense>
</ErrorBoundary>
```

`WidgetFallback` 使用 Tailwind 的 `animate-pulse` 渲染灰色占位块，在深色/浅色模式下均有良好的视觉表现。

## 11. 功能模块: 我的日常

### 11.1 概述

"我的日常" (`/daily`) 是个人自助工作台模块，聚合当前用户的 HR、财务、OA 数据到一个卡片网格页面。它复用现有后端 API (HR 请假/考勤/薪资、财务报销)，并新增 OA 通知和用车申请两组 API。

**设计模式:** Pattern A -- 聚合式个人视图。不改变现有 HR/Finance 管理页面，而是提供同一数据的**个人视角**。

### 11.2 页面布局

Monday.com 风格卡片网格 (桌面 4 列，移动端 2 列)。每张卡片: 白色背景、彩色左边框、图标+标题+指标数字+操作按钮。

```
第 1 行: [请假申请] [报销申请] [待我审批] [通知公告]
第 2 行: [考勤打卡] [薪资查询] [用车申请]
```

### 11.3 七大功能卡片

| 序号 | 卡片 | 指标 | 操作 | 展开方式 | API |
|------|------|------|------|----------|-----|
| 1 | 请假申请 | 剩余年假天数 | 发起请假 | Drawer | `GET/POST /api/hr/leaves` |
| 2 | 报销申请 | 待处理报销数 | 发起报销 | Drawer (含 AI 发票识别) | `GET/POST /api/finance/expenses` |
| 3 | 待我审批 | 待审批总数 | 去审批 | Inline 展开 | 聚合 leaves + expenses + vehicle |
| 4 | 通知公告 | 未读通知数 | 查看全部 | Inline 展开 | `GET /api/oa/notices` |
| 5 | 考勤打卡 | 今日打卡状态 | 打卡 | Inline 日历视图 | `GET/POST /api/hr/attendance` |
| 6 | 薪资查询 | 最近月净薪资 | 查看工资条 | Inline 展开 | `GET /api/hr/salary` |
| 7 | 用车申请 | 待处理申请数 | 申请用车 | Drawer | `GET/POST /api/oa/vehicle-requests` |

### 11.4 Drawer 交互模式

表单类操作 (请假、报销、用车) 使用右侧 Drawer 面板展开，保持卡片网格可见以提供上下文。Drawer 中包含:

- 表单区域 (顶部)
- 我的历史记录列表 (底部，含状态标签)

### 11.5 AI 发票识别

报销申请 Drawer 内置 AI 发票识别功能:

1. 用户在上传区域拖放/选择发票文件
2. 文件上传至 `POST /api/finance/expenses/parse-receipt`
3. 显示 "AI识别中..." 加载状态
4. 返回结果自动填充表单 (金额、日期、类别、商户、描述)
5. AI 填充字段以蓝色微光高亮标识
6. 用户审核后提交

**返回格式:**

```json
{
  "amount": 358.00,
  "date": "2026-03-10",
  "category": "travel",
  "vendor": "滴滴出行",
  "description": "项目出差交通费",
  "confidence": 0.92
}
```

> 当前为 Mock 实现，接口设计已为未来接入真实 OCR/LLM 预留。

### 11.6 数据管理

使用独立的 `dailyStore.ts` (Zustand) 聚合所有 API 调用，按当前用户 ID 过滤数据。当前用户模拟使用硬编码 ID (`EMP001`)，与系统 Demo 定位一致。

## 附录: 预留可配置能力

当前实现为固定布局，但架构上已预留以下扩展点:

| 预留字段 | 位置 | 未来用途 |
|----------|------|----------|
| `WidgetSlot.area` | PageLayout 配置 | CSS Grid 区域命名，支持复杂网格 |
| `WidgetSlot.className` | PageLayout 配置 | 控制 slot 跨列/跨行 |
| `WidgetDef.defaultSize` | Registry | 网格占用尺寸 (cols x rows) |
| `PageLayout.grid` | PageLayout 配置 | 支持多种网格模板 |

未来如需实现用户拖拽布局，只需替换 PageRenderer 的渲染逻辑，控件层和数据层无需变动。
